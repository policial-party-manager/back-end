## Problem Statement

学院党支部目前用 Excel、Word 和纸质材料管理党员发展全过程。结果是：学生信息分散在不同支委的表格里、没有统一标准；培养时间线（谁是积极分子、培养了多久、思想汇报交了几次、党课学了什么）靠人工记忆和纸质记录；组织生活会和主题党日靠纸质签到表；支委换届时历史资料要重新整理，往届学生的培养轨迹查不回来；各类统计（各阶段人数、活动参与率、二课学时）只能人工数。

后端已经完成了这个系统的一半：认证（含学校 CAS）、用户/支部/角色、活动、新闻公告、操作日志、Excel 批量导入、活动签到与报名、思想汇报审阅流、党校学习记录、政治身份两阶段变更。**但支委（`branch_admin`）在成员管理和活动管理上全是 403**，等于真实支部里最需要干活的那个人用不了系统；**培养联系人根本不存在**，思想汇报的审阅人被硬编码成支部书记一人；**活动的「参与范围」没有写入口**，导致「谁该来而没来」算不出来，活动统计只剩签到人数一个数；**请假没有地方落**，考勤四态里三态无法表达。

换句话：系统能录入事实，但**回答不了支委真正要问的问题**——「这一批积极分子谁该转发展对象了」「这次组织生活会谁没来」「这个人的培养档案齐不齐」。

## Solution

把后端从「能录入」推进到「真实支部能连续用一学期」：补上支委的权限面与数据隔离，让支部真正能自己运转；补上培养域（培养联系人、培养材料），让「谁带的、带了什么」有据可查；补上活动的参与范围与请假，让考勤四态与「谁没来」成为可计算的；补上二维码签到的签发与校验，让签到从手工点名单变成扫码；把统计收敛到只做能驱动动作的那几个数。

九个能力块，全部建立在既有 `/api/v1|v2|v4` 前缀与 `openapi.yaml` 唯一契约之上，不新增版本号。

## User Stories

### 支委权限与数据隔离

1. 作为支委，我想看到本支部全部成员的列表，以便不用再向老师要名单。
2. 作为支委，我想按姓名、学号、年级、专业、政治身份、当前阶段筛选本支部成员，以便快速定位某个人。
3. 作为支委，我想查看本支部成员的基本信息，以便核对资料是否齐全。
4. 作为支委，我想修改本支部成员的手机号、邮箱、备注等联系方式，以便成员换号后不用找老师。
5. 作为支委，我想导出本支部成员名单为 Excel，以便线下开会时用。
6. 作为支委，我想在导出时只导出筛选后的结果，以便导出的表就是我要的那批人。
7. 作为支委，我想创建本支部的活动，以便不用每次都请老师代发。
8. 作为支委，我想编辑本支部尚未开始的活动，以便临时改时间地点。
9. 作为支委，我想查看本支部活动的报名情况，以便知道有多少人来。
10. 作为支委，我想查看本支部活动的签到记录，以便核对谁到了。
11. 作为支委，我想为本支部活动生成签到二维码，以便现场扫码。
12. 作为支委，我想导出本支部活动的签到名单，以便存档。
13. 作为支委，我**不能**看到其他支部的成员、活动与签到记录，以便支部之间互不干扰。
14. 作为支委，我**不能**删除活动、不能查看全院活动，以便这些破坏性/全局能力仍归老师。
15. 作为支委，我**不能**修改成员的学号、姓名、学院、所属支部、政治身份，以便这些权威字段不被越权改动。
16. 作为超级管理员，我想管理全院所有支部的成员与活动，以便统筹。
17. 作为超级管理员，我想指定谁是某个支部的书记，以便思想汇报有明确的审阅人。
18. 作为超级管理员，我想在指定书记时被强制要求该用户持有支委角色，以便不会出现「是书记但没权限」的死角。
19. 作为普通成员，我想只能看到自己的资料与培养信息，以便隐私不被同支部同学看到。

### 参与范围与活动统计

20. 作为支委，我想在新建活动时指定参与范围（政治身份、年级、学院，可组合），以便活动只面向该来的人。
21. 作为支委，我想让「不限年级」可以被表达，以便面向全院的党课不用逐年级建多条范围。
22. 作为支委，我想在活动详情里看到应到人数，以便心里有数。
23. 作为支委，我想看到参与率（实到/应到），以便向上汇报。
24. 作为支委，我想看到签到名单、缺席名单、请假名单三张表，以便逐人核对。
25. 作为支委，我想缺席名单是「应到范围内没有签到也没有请假的人」，以便不会把请假的人误判成缺席。
26. 作为支委，我想在活动结束后看到统计自动生成，以便不用手工数。
27. 作为支委，我想复制上个月的组织生活会生成新活动，以便每月重复的活动不用重填。
28. 作为普通成员，我想只看到我符合参与范围的活动，以便不被无关活动打扰。
29. 作为普通成员，如果我的政治身份还没登记，我想在报名受限活动时看到可执行的提示，以便知道该去找谁登记。

### 请假与考勤四态

30. 作为支委，我想在活动开始前为某个成员录入请假（含理由），以便他知道来不了时不占用缺席名额。
31. 作为支委，我想修改或撤销我录入的请假，以便成员临时又能来了。
32. 作为支委，我想请假记录保留录入人、录入时间、理由，以便事后追溯。
33. 作为支委，我想考勤状态能区分「正常签到 / 请假 / 缺席 / 迟到」四态，以便统计口径与文档一致。
34. 作为支委，我想「迟到」由系统根据签到时间与签到开始时间自动判定，以便不用手工标注。
35. 作为普通成员，我想在扫码签到时如果已请假，收到明确提示，以便不会重复操作。
36. 作为普通成员，我想在迟到时签到仍然成功但被标记为迟到，以便不被拒绝入场。

### 二维码签到

37. 作为支委，我想为进行中的活动生成签到二维码，以便现场投屏。
38. 作为支委，我想二维码每 60 秒自动失效并刷新，以便截图转发给别人无法签到。
39. 作为超级管理员，我想配置二维码有效期，以便不同场合用不同窗口。
40. 作为普通成员，我想扫当前有效的二维码完成签到，以便不用排队签纸质表。
41. 作为普通成员，我想同一个二维码能被现场所有人扫，以便不用一人一码。
42. 作为普通成员，我想重复扫码时收到「您已完成签到」，以便知道已经签过。
43. 作为普通成员，我想在签到未开始、已截止、活动已结束时收到明确提示，以便知道为什么签不了。
44. 作为普通成员，如果我不在活动的参与范围内，我想收到「您无权参与本次活动」，以便不会误签。
45. 作为支委，我想签到人数实时增加，以便现场就知道到了多少人。

### 培养联系人

46. 作为支委，我想为成员指派 1~2 名培养联系人，以便培养关系有明确责任人。
47. 作为支委，我想修改成员当前的培养联系人，以便联系人换人时能更新。
48. 作为支委，我想批量设置一批成员的培养联系人，以便新确定一批积极分子时不用逐人点。
49. 作为支委，我想在成员培养主页看到当前培养联系人，以便一眼知道谁在带。
50. 作为支委，我想在查看思想汇报时看到提交人当前的培养联系人，以便知道该找谁了解情况。
51. 作为培养联系人本人，我想看到我带教的成员列表，以便知道自己要跟谁谈话。
52. 作为支委，我想培养联系人是「当前关系」而不是历史快照，以便换人后旧思想汇报自动归属新联系人。
53. 作为超级管理员，我想培养联系人只能由组织指派、成员本人不能自改，以便它与「紧急联系人」不被混淆。

### 培养材料与电子档案

54. 作为支委，我想为成员上传培养材料（PDF / Word / 图片 / ZIP），以便入党申请书、政审材料、培训证书有地方存。
55. 作为支委，我想给每份材料标注类型，以便档案里能按「入党申请书 / 思想汇报 / 政审材料」分类。
56. 作为支委，我想看到成员的全部培养材料列表，以便检查档案是否齐全。
57. 作为支委，我想删除传错的材料，以便不留下垃圾文件。
58. 作为支委，我想在一个页面看到成员完整的培养档案（基本信息 + 身份历史 + 思想汇报 + 活动参与 + 学习记录 + 培养材料 + 培养联系人），以便不用在多个模块间跳。
59. 作为支委，我想把这个完整档案以 JSON 返回，以便前端自己排版打印。
60. 作为普通成员，我想看到自己的培养档案，以便知道自己还差什么。

### 统计

61. 作为超级管理员，我想在首页看到待审核思想汇报数量，以便知道有几件事等我做。
62. 作为超级管理员，我想在首页看到待审批身份调整数量，以便及时处理。
63. 作为支委，我想在本支部首页看到同样两个待办数，以便只处理我该处理的。
64. 作为支委，我想看到各阶段人数分布，以便知道本支部的梯队结构。
65. 作为超级管理员，我想看到全院各支部的人数与各阶段分布，以便统筹。
66. 作为支委，我想统计支持按学院、专业、班级、年级维度切分，以便按需汇报。
67. 作为普通成员，我想看到自己的学时与活动参与汇总，以便知道自己够不够。

### 审计与批量

68. 作为超级管理员，我想在审计日志里看到每次成员数据修改的「修改前」与「修改后」内容，以便追溯是谁改错了。
69. 作为超级管理员，我想审计日志记录操作类型、操作对象、操作人、IP、结果，以便满足文档的审计要求。
70. 作为超级管理员，我想在 Elasticsearch 不可用时审计仍以应用日志形式保留，以便本地开发不阻塞。
71. 作为超级管理员，我想批量停用成员，以便毕业/转出的人不再出现在名单里。
72. 作为超级管理员，我想批量恢复被停用的成员，以便误停时能撤回。
73. 作为超级管理员，我想批量调整成员所属支部，以便转专业/支部调整时不用逐人改。
74. 作为支委，我想批量设置培养联系人，以便成批操作。
75. 作为操作者，我想任何批量操作都逐条返回成功/失败明细，以便知道哪几条没成功。
76. 作为操作者，我想单次批量超过 200 条时被拒绝并提示分批，以便不会超时或部分写入。
77. 作为操作者，我想批量操作沿用 Excel 导入那种「部分成功」的结果结构，以便前端只用处理一种结果格式。

### 历史不可删

78. 作为超级管理员，我想身份变更历史不能被任何接口删除，以便发展轨迹永远可追溯。
79. 作为超级管理员，我想系统里不存在删除身份变更记录的 HTTP 端点，以便不会被误操作。
80. 作为超级管理员，我想身份变更单据有一个「作废」状态域留给运维修正，以便录入错误有兜底路径。

## Implementation Decisions

### 域模型与词表

- 严格使用 `GLOSSARY.md` 既有词汇：**当前政治身份**、**变更单**、**秘书 = 审阅人**、**软删除**、**不存在语义**、**file: 前缀**、**role_id（身份字典）**、**契约基线**。
- 本 spec 新增并已写入词表的对立词条：**培养联系人 ≠ 紧急联系人**。前者是组织指派的培养责任人（1~2 名，可被思想汇报与培养记录关联），后者是成员自填的 `contact_person`，成员可改。两者不可合并存储。

### 块1 培养联系人

- 新建关系表 `tb_user_mentor`：`user_id`（被培养人）、`mentor_id`（培养联系人，指向 `tb_user`）、`status`（1 正常 / 0 已删除）、时间戳。`(user_id, mentor_id, status=1)` 施加唯一约束，并在服务层强制「同一被培养人最多 2 名在职联系人」。
- 不把 `mentor_id` 写进 `tb_thought_report`：思想汇报道出「提交人**当前**的培养联系人」而非历史快照。换联系人后旧汇报的归属随之更新，这是裁定行为，不是缺陷。
- 端点归属 `/api/v4/admin/users/*`（成员域），不新开前缀：单个指派/移除、批量指派、按成员查询、按联系人反查带教名单。
- 培养联系人只能由超管/支委指派；成员个人中心**不提供**该字段的写入口。

### 块2 培养材料

- 新建 `tb_cultivation_material`：`user_id`、`material_type`（字典或自由文本枚举：入党申请书/思想汇报/政审材料/培训证书/其他）、`file`（沿用 **file: 前缀** 约定）、`uploader_id`、`remark`、`status`（软删除，默认 1）、时间戳。
- 复用既有上传端点产出 `file:` 路径，不新建上传通道。
- 端点归属 `/api/v4/admin/users/{id}/materials`，删除走软删除（`status=0`）。

### 块3 参与范围

- `tb_activity_identity.grade` **放宽为可空**：`NULL` 表示不限年级。改动需按既有 MySQL 经验先 DROP FK 再 MODIFY 再 ADD FK（该表被 FK 引用的是 `activity_id` 与 `target_identity`，`grade` 本身不受 FK 约束，但需与 `schema-verify.sh` 一致）。
- 为活动创建/编辑请求与活动 VO 补上参与范围字段（政治身份、年级、学院，三者可各自为空=不限），管理员从此可通过 API 设置参与范围，不再依赖裸 SQL。
- 参与范围的三维匹配规则复用报名侧已固化的语义（#61）：行上非空字段才参与校验，全空=不限。

### 块4 签到校验与考勤四态

- 签到校验从三项扩到四项：登录 → **属于参与范围** → 未重复 → 处于签到时间窗。第四项通过注入活动范围校验器实现，与报名侧共用同一份范围判定逻辑（避免两套口径）。
- 考勤四态的表达：**正常签到** = 有 `sign_record` 且签到时间 ≤ 签到开始时间；**迟到** = 有 `sign_record` 且签到时间 > 签到开始时间（**查询时推导，不落字段**）；**请假** = 有生效请假记录；**缺席** = 在应到范围内，既无签到也无请假。
- 新建 `tb_activity_leave`：`activity_id`、`user_id`、`reason`、`operator_id`（录入人）、`status`、时间戳。不把请假塞进 `sign_record.sign_type`——「已发生的事实」与「已批准的预期」生命周期不同。`(activity_id, user_id, status=1)` 唯一。
- 已请假的人签到：允许签到成功（人到场了是事实），但提示已存在请假记录；统计口径上以签到为准，即现场到了就不算请假。

### 块5 二维码签到

- token 存 Redis：键 `sign:activity:{activityId}`，值为随机不可预测串，TTL 由配置项控制（默认 60 秒）。过期后旧 token 立即失效，这是「防截图转发」的唯一实现方式。
- **一个有效 token 可被该活动的所有参与者使用**，不是一次性凭证：token 证明的是「此刻在场」，不是「谁抢到了」。防重复靠 `(activity_id, user_id)` 唯一约束，不靠 token 一次性。
- 端点：生成二维码（支委/超管，返回当前 token 与过期时间）、扫码签到（登录成员，携带 token）。签到成功后统计数实时可见。
- 不做地理围栏。

### 块6 权限与支部隔离

- **鉴权判据改为成员所属支部**（`tb_user_detail.branch_id`），不再用 `tb_branch.secretary_id`。`secretary_id` 的用途收窄为「派定思想汇报审阅人」，这条已被既有实现与测试固化，不动。
- 支委可操作的范围：本支部成员（查看/改联系方式/导出）、本支部活动（创建/编辑/查报名/查签到/生成二维码/导出）。
- 支委不可操作：删除活动、查看全院活动、改成员的学号姓名学院所属支部政治身份、导入 Excel、管理支部与角色。
- 类级 `@PreAuthorize` 下沉到方法级，逐项对齐文档权限矩阵；不允许出现「整个类都超管专属」而其中若干方法文档明确允许支委的情况。
- 新增约束：指定支部书记时校验该用户持有支委角色，否则拒绝。这消除「是书记但没有 branch_admin 权限」的死角。
- 越权统一沿用 **不存在语义**：支委读取其他支部的成员/活动/签到，返回「XX不存在」。

### 块7 统计

- 只做能驱动动作的统计，纯展示类（本月新增党员数、本周活动数）不做。
- 首页待办两项：待审核思想汇报数、待审批身份变更数，支委版限本支部，超管版为全院。
- 阶段分布：各政治身份人数，支持按学院/专业/班级/年级切分。
- 活动统计三张名单 + 参与率（实到/应到），应到 = 参与范围匹配的全员。
- 培养档案聚合：单个端点返回完整档案 JSON，供前端自行排版打印。

### 块8 审计

- 继续用 Elasticsearch 通道（已在运行），给日志文档加「修改前数据」「修改后数据」两个字段。
- 删除 MySQL 侧死表 `tb_operation` 与其 Mapper——该通道从未被写入。

## Testing Decisions

好测试的标准：**只验证外部可观察行为，不验证实现细节**。具体到本仓：不断言某个私有方法被调用、不断言字段名、不断言内部类结构；断言 HTTP 状态码、响应体内容、数据库最终状态。

接缝按优先级（**不新建任何测试基建，四个全部是仓内已有**）：

1. **MockMvc + 完整 Spring 安全链**（最高接缝，承载本 spec 的主要风险）
   - 为什么必须在这一层：支委权限、支部数据隔离、批量端点、扫码流程的失败模式在 service 层完全不可见——`AccessDeniedStatusTest` 的类注释已记录这个教训（service/契约测试直接构造对象，看不见安全链行为）。
   - 覆盖：支委可访问/不可访问矩阵逐项、跨支部读取返回「不存在」、批量上限拒绝、请假与签到的状态组合。
   - 先例：`AccessDeniedStatusTest`。

2. **Service 层 Mockito 单测**（纯计算规则）
   - 覆盖：应到人数计算、迟到判定（签到时间 vs 签到开始时间）、培养联系人「最多 2 名」上限、参与范围三维匹配、请假对缺席名单的影响。
   - 先例：`ActivitySignupServiceImplTest`、`ThoughtReportServiceImplTest`。

3. **反射契约测试**（不变量，不启动上下文）
   - 覆盖：身份变更控制器无删除映射、控制器角色名存在且无空壳、`openapi.yaml` 与代码端点对账。
   - 先例：`ControllerAuthContractTest`、`DeprecatedEndpointContractTest`。

4. **e2e 脚本**（纵向流程补充）
   - 在前述分层测试之外，为「支委完整走一遍：建活动 → 设参与范围 → 录入请假 → 生成二维码 → 成员扫码 → 看统计」补一条端到端链路。
   - 先例：`scripts/e2e-acceptance.sh`（自清理、可重复执行、30 断言）。

## Out of Scope

- 前端实现（本仓只做后端）。
- 微信小程序端：本仓只交付二维码 token 的签发与校验接口。
- 智能导航助手（文档 §3.8）：无外部依赖价值，成本高。
- 电子培养档案导出 PDF：前端自行排版打印，后端只出 JSON。
- 地理围栏：已显式裁定不做。
- 短信验证码通道：已在 `.out-of-scope/sms-verification.md` 判 wontfix。
- 将登录模型改为纯 SSO（文档 §2.2.1 说「不保存密码」）：现有密码 + 邮箱码 + 手机码 + CAS 四通道保留，该冲突不在本期解决。
- 公告置顶（`tb_notice_top`）与活动类型「是否计入档案」（`count_to_file`）：另开需求票。
- 支部管理员以外的角色细分（学院管理员、组织员）：RBAC 可扩展但本期不做。
